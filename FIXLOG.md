## 2026-07-27
Fixed: Achiote Paste showing "NaN" for its expected stock and crashing the Inventory page (which looked like being logged out, but you weren't). Root cause: whenever a stock quantity gets adjusted, a data-cleanup step in the save code was accidentally corrupting the "add/subtract this amount" instruction into garbage before it reached the database — so instead of the number going up or down, the stock field got overwritten with junk data instead of a number. Achiote's stock field was fixed back to its correct value (15g, confirmed from the last stocktake's own before/after record — before 2000g, a stocktake correction of -1985g, landing at 15g). The underlying save bug is now fixed so this can't happen again. Also added two safety nets: any screen that shows stock numbers now falls back to 0 instead of breaking if it ever sees bad data again, and the app itself now recovers gracefully from any unexpected screen error instead of the whole app disappearing (which is what was reading as "logged out").
Checked: Ran a full production build and type check — both clean, no errors introduced. Traced the exact crash by hand: the Inventory page was rendering the corrupted stock value directly, which React refuses to do and throws — with no safety net anywhere in the app, that throw wiped the entire screen. Confirmed Achiote's corrected value matches its own stocktake history exactly before writing it.
Still needs you: while checking for this same problem elsewhere, found 30 other inventory items with the exact same kind of corrupted stock field — but their case is different and needs a decision, see NEXT_UP.md.

## 2026-07-27 (3)
Fixed: The actual bug that caused the 30-item corruption above — completing a stock count for an item measured in kg or litres, where the count confirmed nothing had changed, was writing a wildly inflated number to stock (roughly 1000x too high) instead of correctly leaving it alone. Root cause: the completion step was treating the system's own already-correct stock figure as if it were a fresh number someone had just typed in, and running it through a unit conversion a second time. Fixed so that whenever a count confirms no real change, the screen writes back the exact existing figure with no conversion at all — only counts that actually differ from the system now go through the conversion step, exactly as before. This is a different bug from the one fixed earlier this session (that one was in how adjustments got saved to the database; this one is in the Stock Take screen's own counting logic) — confirmed they don't share any code.
Checked: Ran a full production build and type check — both clean, no errors introduced. Traced both scenarios by hand: a "no change" count on a kg-measured item now writes back its exact existing stock figure instead of an inflated one; a real count change (the same shape as Achiote's earlier correction) still goes through the same conversion logic as before, completely untouched by this fix — confirmed identical behavior to before the change.
