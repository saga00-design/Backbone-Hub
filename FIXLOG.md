Also added two safety nets: any screen that shows stock numbers now falls back to 0 instead of breaking if it ever sees bad data again, and the app itself now recovers gracefully from any unexpected screen error instead of the whole app disappearing (which is what was reading as "logged out").
Checked: Ran a full production build and type check — both clean, no errors introduced. Traced the exact crash by hand: the Inventory page was rendering the corrupted stock value directly, which React refuses to do and throws — with no safety net anywhere in the app, that throw wiped the entire screen. Confirmed Achiote's corrected value matches its own stocktake history exactly before writing it.
Still needs you: while checking for this same problem elsewhere, found 30 other inventory items with the exact same kind of corrupted stock field — but their case is different and needs a decision, see NEXT_UP.md.

## 2026-07-27 (4)
Fixed/Added: Built "Receive Delivery" — a proper goods-in step for Stock Orders. Previously, marking an order "Received" just changed a label and did nothing else; there was no record of what actually arrived, and it was the Invoice screen that silently updated stock instead, with no link back to what was actually delivered. Now, receiving a delivery opens a checklist of everything on that order, defaulted to the full ordered amount — you adjust any line that came up short, confirm, and that's what updates stock (not the invoice). Every receiving session is saved permanently, including lines that never arrived at all, so nothing gets silently lost. This is the foundation piece needed before Invoice Processing can be changed to check invoices against what was actually received, rather than just trusting the invoice blindly.
Also fixed along the way: Stock Orders were never actually being loaded back from the database — only orders placed in the current browser session showed up, so reloading the page (or coming back the next day) made any "Sent" order impossible to receive against. That's now fixed; order history persists properly, which the Reports screen benefits from too.
Checked: Ran a full production build and type check — both clean. Traced three scenarios by hand: a delivery that matches the order exactly (stock increases by the full ordered amount, order marked Received); a short delivery where one line is reduced (stock only increases by what was actually entered, that line is visibly flagged before confirming, and the shortfall is preserved on the saved record for later reference); and a line entered as zero-received (correctly written to the record as "ordered but never arrived," with no stock change and no stray database write for that line).
Still needs you: this only covers goods-in. Invoice Processing itself hasn't been changed yet — it's still the one updating stock today. That's the next step, and it's now unblocked.
Files touched: types.ts, firestore.rules, App.tsx, components/Orders.tsx, components/ReceiveGoodsModal.tsx (new)

## 2026-07-27 (6)
Fixed/Added: Invoice Processing no longer touches stock at all — approving an invoice used to add straight to stock levels, completely separately from (and duplicating) whatever Receive Goods had already logged. Now Receive Goods is the only thing that ever changes how much stock you have; Invoice Processing's job is purely financial. Approving an invoice now opens a proper review screen: you can link the invoice to the Stock Order it's for, and it checks the invoiced quantity against what was actually ticked as received, and checks the price against what you last paid THIS SAME SUPPLIER for THIS SAME ITEM (buying the same thing from two different suppliers at different prices is never treated as a false price-change alert — each supplier has its own running price history). Anything that doesn't match is flagged clearly and has to be individually ticked off as "reviewed" before you can approve — nothing gets waved through by one blanket Approve button. Approving still updates the item's price and logs the price into that supplier's history, same as before, just never quantity.
Also fixed along the way: Invoices, like Stock Orders before them, were never actually being loaded back from the database — only the ones processed in your current session showed up, so reloading the page lost access to anything still Pending. Also, toggling an invoice's payment status, rejecting it, or deleting it never actually saved to the database at all, only to the screen — any of those would have silently reverted on reload. Both are now fixed.
Checked: Ran a full production build and type check — both clean. Traced three scenarios by hand: an invoice that matches its Receive Goods record exactly with no price change (approves immediately, no checkboxes needed); an invoice invoiced for more than was actually received (flagged clearly, Approve stays disabled until the mismatch is ticked as reviewed); and a genuine price increase from a known supplier (flagged with the correct direction, £ amount, and percentage) — and confirmed a second, different supplier's price for the exact same item was never pulled into that comparison.
